# 客户端运行时架构

本文描述 `client` 包所依赖的不变量。公共 API 的使用说明见 `README.mbt.md`。

## 所有权模型

`Client::create(config)` 只分配共享队列、内置类型信息和可重复等待的就绪状态，
不会打开套接字。它返回可复制的 `Client` 和只能运行一次的 `ClientExecutor`。
调用方在任务组中启动 `run()`；执行器负责连接、认证、发布启动信息，然后运行
套接字驱动器。`Client::ready()` 与异步数据库操作都会等待启动完成；在此之前
同步读取参数或取消令牌会返回 `NotReady`。重复运行执行器返回
`ExecutorAlreadyStarted`。

启动成功前，传输层所有权由连接建立流程持有。TLS 协商、身份认证、启动协议或
连接超时失败时，会关闭已建立的传输层连接，再向所有就绪等待者发布同一错误。
执行器启动前关闭或中止客户端不会打开套接字。

`Stream` 的安全连接变体同时保留 `Tls` 和原始 `Tcp`。TLS 读写使用 `Tls`，但资源释放时
会先调用 `Tls::close()`，再调用 `Tcp::close()`：TLS API 只释放协议资源，不会关闭
底层传输连接。资源释放刻意不执行异步 TLS 关闭交互，以确保取消和错误展开期间
始终能够同步释放传输层资源。

驱动器是私有的。共享状态只保存其任务句柄，使 `Client::abort()` 可以在启动期间
或运行期间同步请求取消。执行器只在 `run()` 的局部作用域持有任务组。驱动器负责
所有套接字读取、普通前端消息写入，以及提示、通知和参数状态更新的发布。

## 单操作执行不变量

一个 PostgreSQL 会话同一时刻只允许一个逻辑操作处于活动状态。公共入口在提交协议工作前，
按先进先出（FIFO）顺序获取 `OperationGate` 许可。等待期间发生取消时，会移除对应的
等待者，且不会错误地转移所有权。

许可覆盖整个逻辑操作，而非单条前端消息：

- 预处理、参数类型查询、执行和清理共享同一个上下文
- 流持续持有上下文，直到 EOF、结束或转交给分离的排空任务
- COPY IN 持续持有上下文，直到完成或中止
- 事务持续持有上下文，直到提交或回滚
- 嵌套事务在各个保存点作用域之间传递同一个上下文

内部各阶段接收私有的 `OpContext`，并调用其内部方法。它们绝不能重新进入公共 `Client`
方法并再次获取门控许可。这一点对类型解析发起的系统目录查询，以及临时预处理语句的
清理尤为重要。

## 驱动器与队列

驱动器在连接建立后的整个生命周期维持一个套接字读取任务，包括空闲时段。
提示、通知和参数更新会立即发布；普通响应经容量为一的队列交给请求循环。
请求循环每次处理一个 `Request`：

1. 接收并保留下一个已接受操作的请求
2. 写入该请求的前端协议字节
3. 将每条普通响应路由到该请求的有界响应队列
4. 持续处理，直到收到 `ReadyForQuery` 或到达该请求协议规定的终止状态
5. 转而处理下一个请求

驱动器不维护待处理请求列表，不会择机启用流水线，也不会按最早请求来路由响应。

每个请求的响应队列始终有容量上限（目前为八条消息）。读取任务到请求循环的队列
最多缓存一条消息，活动响应的消费者停滞时，背压仍会限制套接字读取和内存占用。
由于同一时刻只执行一个操作，后续请求无法绕过停滞的消费者。

COPY IN 是协议中的例外，需要双向协调。其生产者队列最多容纳八个动作。PostgreSQL
进入 COPY 模式后，驱动器会为该请求创建且仅创建一个写入任务，用来处理数据、完成或
中止动作，而读取任务仍是唯一的后端消息读取者。提前到达的 `ErrorResponse` 会被
转发给写入端（sink），输入队列随即被清空并关闭，写入任务则在完成当前整个帧的写入后
停止。驱动器会等待该写入任务结束，然后才转发最终的 `ReadyForQuery` 或开始另一个请求。
整个过程仍然属于同一个逻辑操作。

## 流与分离

行流、简单查询流和 COPY OUT 流持有操作许可。

- 自然到达 EOF 时释放许可
- `finish()` 排空至操作边界，然后释放许可
- `detach()` 将响应队列和许可交给执行器控制队列调度的排空任务
- 分离后调用 `finish()` 会等待该排空任务完成

清理是幂等的。消费者取消时，既不能泄漏许可，也不能让下一个操作在 PostgreSQL
到达安全边界之前开始。

六个 `Client::with_*` 流/COPY API 共用 `with_scoped_resource`。等待就绪和获取许可仍可
取消；仅协议启动和 finalizer 受到取消保护，业务回调保持可取消。资源获取后立即安装
`errdefer`，在回调前、回调后和清理后检查待处理取消。输出流调用 `finish()`；COPY IN
若未显式完成则调用 `abort()`。COPY IN 记录遗弃排空的完成信号，作用域因此也能等待
`send`、`finish` 或 `abort` 被取消时启动的后台清理。清理错误不覆盖回调原错误。
Client 的 Statement 作用域和事务的 Portal 作用域仅拥有本次执行流，不关闭父句柄。

inferred/typed 临时查询在 `read_prepare_response` 成功后立即安装语句清理。Close 字节和
执行参数均在提交 Execute 前构造；随后由不会抛错的 RowStream 构造器接管清理责任。
编码或提交失败时，使用已有许可关闭语句，并保留原始错误。

命名 `prepare` 使用专门的句柄交付路径：客户端或事务在受保护的准备过程结束后，仍持有
许可和 `OpContext`，然后检查待处理取消。若已取消，就受保护地发送 Close 并等待
`ReadyForQuery`，再传播取消。任何 Close 失败都会中止物理连接，但调用方仍收到原取消。

裸流工厂在获取许可后、开始协议工作前检查是否存在待处理的取消。对异步预处理或 COPY
启动过程施加取消保护的工厂，会在离开保护区域后、仍处于同一个 `errdefer` 作用域内时
再次检查。流尚未创建时，该作用域会在失败时释放许可。一旦流已经创建，取消就会将流和
许可交给分离的排空任务，而不是返回失去归属的句柄，或过早释放连接。

分离的流保存可重复等待的完成状态，而不保存任务句柄。执行器的控制任务独立接收
排空作业；即使八条消息的响应队列已满，驱动器也不会阻止排空调度。预期的 `Closed`
错误供 `finish()` 读取，不会使执行器失败。数据库错误保留在流状态中；意外错误会
使执行器失败。控制队列关闭后，`finish()` 会同步排空并取得最终结果或错误。
执行器退出时，控制队列也会向尚未开始的排空作业发布关闭结果，避免 `finish()`
无限等待。

MoonBit 任务取消有独立的生命周期规则。一旦 `execute_raw` 持有结果流，其错误清理
就会在取消保护下持续排空至 `ReadyForQuery`。随后，外层的 `execute` 才关闭临时
预处理语句。这个顺序确保在等待语句关闭之前，先解除有界响应队列的背压。清理错误不会
覆盖原始错误或取消，且 `execute_raw` 绝不会关闭由调用者持有的预处理语句。排空可能
需要等待 SQL 命令执行完毕；仅取消任务并不会要求 PostgreSQL 中断该命令。

`Driver::run` 在正常关闭、普通错误和取消时，都会执行同步且幂等的退出清理。它会关闭
活动请求及排队请求的响应队列、COPY 输入队列、提交队列、通知队列和套接字，并将运行时
标记为已关闭。普通驱动器错误会传递给等待中的请求；取消则向这些请求传递
`ClientError::Closed`，同时保留驱动器自身的取消。驱动器退出时的 defer 清理会唤醒所有消费者，包括处于取消保护中的消费者。
执行器在局部任务和传输层清理结束后发布可重复等待的终态，且不会覆盖此前的失败。

## 事务

开始事务时，许可从 Client 调用转移至 `Transaction`。事务方法使用同一个私有上下文。
只有提交或回滚到达 `ReadyForQuery` 后，许可才会释放。

通过外层 Client 的其他克隆提交的调用，会排在事务之后等待。嵌套事务使用保存点，
并将同一个上下文临时转交给子事务。

回调式事务在发生错误或任务取消时回滚。回滚受取消保护，并且会在释放所持有的许可之前完成。

async 0.22 在离开受保护代码块时，不会自动传播待处理的取消。客户端和事务会在操作边界
检查取消：包括开始新工作之前，以及最外层保护结束之后。回调式事务还会在自动提交前
检查取消。如果调用者在外层设置了保护，这些检查会有意推迟到该保护自身的边界。
若 `BEGIN` 或 `SAVEPOINT` 成功后，在交付句柄前发生取消，则会在仍持有原始许可的
情况下执行回滚。对于已经提交给服务器的 `COMMIT`，会先排空响应并根据服务器结果
记录其状态，然后再传播取消。

## 异步消息

带外后端消息绝不会进入操作响应队列：

- `NoticeResponse`
- `NotificationResponse`
- `ParameterStatus`

它们会更新共享状态，并通过 Client 的异步消息队列发布。`Client::next_message()`
采用单消费者语义，在驱动器终止时返回 `None`。即使没有查询在执行，读取任务也会
持续交付这些消息。

`pgpool` 在启动物理连接前安装内部异步消息处理器，将消息转发到连接池的缓冲队列，
而不是 Client 队列；连接池通过 `Pool::next_message()` 消费这些消息。

## 失败与关闭

致命的套接字或协议错误会成为共享状态中的终止状态。驱动器会：

1. 使活动请求失败
2. 使已接受但尚未发送的请求失败
3. 让等待门控许可的操作获取许可，并观察到运行时已关闭
4. 关闭异步消息队列

`Client::close()` 会封闭门控，阻止新工作进入，按 FIFO 顺序等待已接受的操作完成，
随后提交 `Terminate`，并等待驱动器退出。重复调用 close 会等待同一个结果。
取消某个 close 调用者，不会撤销已经开始的关闭流程。

`Client::abort()` 则会立即将运行时标记为已关闭，关闭提交队列但保留其中缓冲的请求记录，
并取消已保存的驱动器任务。随后，驱动器的资源释放流程会使活动响应队列和所有缓冲请求的
队列都以相同的 `ClientError::Closed("connection aborted")` 失败。在资源释放完成之前
保留请求记录至关重要：直接清空提交队列会导致排队的调用者收不到终止通知。因此，
`is_closed()` 描述的是运行时是否可用：即使取消仍在展开、驱动器仍在执行最终的物理
传输连接关闭操作，它也已经为 true。

这些状态收敛规则是必要的，只有这样，`pgpool` 才能判断物理连接是否可以安全回收复用。
